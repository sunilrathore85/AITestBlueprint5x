1. Objective

The goal of this test plan is to confirm the quality, functionality, security, accessibility, and reliability of the VWO login dashboard at https://app.vwo.com.

The login dashboard is the entry point to VWO’s experimentation, personalization, and analytics tools. The product vision in the PRD is a secure, intuitive, and efficient login that connects users to the platform and meets enterprise security and user-experience expectations.

Testing checks the PRD business objectives:

  • Secure access to the experimentation platform.
  • Low login friction for adoption and retention.
  • Enterprise security and compliance needs.
  • A clear path for new users into onboarding.

Primary users are digital marketers, product managers, UX designers, and developers. Secondary users are enterprise teams, conversion-rate specialists, and data analysts. Companies range from about 50–200 employees to enterprises with 1000+ employees.

Success targets stated in the PRD, used as release checks where the build exposes them:

  • Login success rate 95% or higher.
  • Login page load under 2 seconds on a standard connection.
  • User satisfaction 90% or higher for the login experience, when that measure is available.
  • No successful brute-force access and no unauthorized session hijacking in the security tests that are in scope.
  • Compliance checks required by the PRD (GDPR, CCPA, enterprise audit support, WCAG 2.1 AA) are evidenced.
  • Login-related support volume is tracked against the PRD target of a 20% reduction. Testing reports defects that would drive support tickets; it does not itself change the business metric.

2. Scope

Scope follows the PRD for the login dashboard. Items listed under Future Enhancements are out of the current phases until they are specified for a build.

In scope

  1. Functional testing. Email and password login, remember me, session handling and timeout, optional multi-factor authentication, enterprise single sign-on, free-trial registration link, and product announcement / light and dark mode entry points described in the PRD.
  2. Data validation. Real-time validation on blur, email format, mobile keyboard behavior for email, password strength and complexity rules, and rejection of invalid input.
  3. Error handling. Clear, actionable messages for failed authentication, and the error-recovery journey (identify the error, offer recovery, confirm success).
  4. Password management. Forgot-password flow, secure reset token, email-based recovery, and enforced password complexity.
  5. User experience. Responsive, touch-friendly layout, auto-focus on the first field, clickable labels, and loading feedback during authentication.
  6. Accessibility. ARIA labels, screen-reader support, keyboard navigation, high-contrast mode, and WCAG 2.1 AA as stated in the PRD.
  7. Branding. VWO design system, professional appearance, and light and dark themes.
  8. Security testing. HTTPS, encryption in transit, hashed password storage behavior as observable from requirements, session token handling, rate limiting against brute force, GDPR and CCPA data-handling expectations, enterprise audit support, and OWASP authentication guidelines. Tests confirm controls and safe failure. They do not include attack procedures.
  9. Performance and load. Login page load within 2 seconds on a standard connection, asset optimization and CDN behavior where observable, support for thousands of simultaneous login attempts, 99.9% availability target, and multi-region access as deployed.
  10. Integration. Transition to the main VWO dashboard after success, login success/failure analytics, customer-support handoff, SAML and OAuth enterprise SSO, optional Google and Microsoft social login, and onboarding / marketing-tool handoff described in the PRD.
  11. Compatibility. Desktop and mobile viewports, light and dark mode, and the browser and OS matrix in Test Environments.
  12. User journeys. New user (arrival, registration call-to-action, post-registration introduction), returning user (remembered credentials, dashboard, previous context), and error recovery.
  13. Regression. After fixes, existing login behavior in the signed-off scope still works.
  14. Phase coverage. Phase 1 core authentication, Phase 2 enhanced UX, Phase 3 enterprise features, matching the PRD implementation phases.

Out of scope for the current phases

  • Future enhancements called out in the PRD and not assigned to Phase 1, 2, or 3: biometric authentication, adaptive risk-based authentication, progressive web app behavior, A/B tests of the login experience, behavior-based personalization of the login screen.
  • Features of the VWO experimentation product that sit behind the dashboard, except the handoff after a successful login.
  • Any environment, URL, role, or integration the PRD does not name and that is not part of the company test-environment matrix below.

Scope can change if the PRD changes or if testing finds gaps. Changes are reviewed before they are added to execution.

3. Inclusions

Primary login

  • Sign in with a valid email and password and land on the VWO dashboard.
  • Reject wrong password, unknown email, empty fields, and malformed email with a clear message.
  • Validate email format and show field feedback on blur.
  • Show password strength and enforce the complexity rules in the PRD.
  • Auto-focus the first field. Labels activate the related input.
  • Show a loading state while authentication runs.

Session and remember me

  • Remember me keeps the session as specified, and a session ends when the configured timeout is reached.
  • Session tokens are issued and used as specified. A logged-out or expired session cannot open the dashboard.
  • Returning users reach their dashboard. Context from the previous session is preserved as the PRD describes.

Password recovery

  • Forgot-password starts a reset that uses a secure token and email recovery.
  • Invalid, expired, or reused reset tokens do not set a new password.
  • The new password must meet complexity rules. Success is confirmed to the user.

Registration path

  • The free-trial registration link is present and reaches signup.
  • After registration, the guided introduction described in the PRD is available.

Multi-factor authentication

  • Optional 2FA can be required for an account that has it enabled.
  • A wrong or missing second factor does not open the dashboard.
  • Accounts without 2FA still complete email and password login.

Enterprise SSO and social login

  • Organizational accounts can sign in with enterprise SSO using SAML and OAuth as specified.
  • Optional Google and Microsoft sign-in follows the PRD.
  • A failed or cancelled identity-provider login stays on a recoverable login state and does not create a VWO session.

Accessibility, theme, and layout

  • Keyboard-only use of every control on the login screen.
  • Screen-reader names via ARIA labels. High-contrast mode remains usable.
  • Layout works on desktop, tablet, and phone with touch-friendly controls.
  • Light and dark mode match the announced themes and stay readable.
  • Visual design stays consistent with VWO branding in the PRD.

Security and compliance checks

  • Login traffic is HTTPS. Authentication data is protected in transit as required.
  • Password values are not returned in page content, client storage readable by script beyond what the PRD allows, or analytics payloads.
  • Rate limiting slows or blocks repeated failed attempts.
  • Error text does not reveal whether a protection control can be bypassed and does not expose secrets.
  • GDPR and CCPA handling and enterprise audit needs are verified against the behaviors the build exposes (consent, data access, audit trail), limited to login.

Performance and availability

  • Login page becomes usable within 2 seconds on a standard connection.
  • Compressed assets, minified CSS and JavaScript, and CDN delivery are confirmed where those artifacts are observable.
  • Concurrent login attempts at the volume the environment can host, toward the PRD target of thousands of simultaneous attempts.
  • Availability is monitored against the 99.9% target. Geographic behavior is checked on the deployed regions.

Integrations and analytics

  • Successful login opens the main VWO dashboard.
  • Login success and failure are available to analytics as specified.
  • A support path exists for login assistance.
  • Onboarding and marketing integrations fire only as the PRD describes for new users.

Boundary, concurrency, and regression

  • Boundary emails and passwords: shortest and longest values the requirements allow, and one step outside those limits.
  • Concurrent sessions for the same account: timeout, remember me, and logout stay consistent.
  • After each fix, the affected Phase 1, 2, or 3 cases are retested, then a smoke pass of login, reset, and dashboard handoff.

5. Defect Reporting Procedure

A defect is a deviation from the PRD, a broken user journey, a failed validation or error message, an accessibility gap against WCAG 2.1 AA as cited in the PRD, a security control that does not meet the PRD, or a technical error on the login dashboard.

Reporting steps:

  1. Record the defect in JIRA with the project template.
  2. Include environment, browser, account type (no secrets), steps, expected result from the PRD, actual result, and severity and priority.
  3. Attach a screenshot or screen recording and any non-sensitive log or request id. Remove passwords, tokens, and personal data before attaching.

Triage assigns severity and priority and routes the ticket to the role that owns the area. The bug triage skill comment shape (problem, severity, priority, how to test, risks) is the comment standard on the ticket.

AreaRole
Triage point of contactTest lead
Login interface, validation, themes, accessibilityFrontend
Authentication, session, reset token, SSOBackend
HTTPS, rate limit, availability, CDN, regionsDevOps

Tracking tool: JIRA. Testers file and retest. Developers investigate and fix. The test lead prioritizes with the team and reports status.

Communication: defects found that day are sent to development management in an end-of-day status email. Stakeholders get status at the cadence agreed at approval. Emails do not include passwords, tokens, or personal data.

Measures: defects found, time to resolve, and percentage fixed and retested. Counts are split by phase (core authentication, enhanced UX, enterprise) and by type (functional, validation, accessibility, security, performance, integration).

6. Test Strategy

Step 1. Write test scenarios and test cases for the inclusions above.

Design techniques:

  • Equivalence class partitioning — valid and invalid email, password, and token groups.
  • Boundary value analysis — password length and complexity limits, field lengths, session timeout edges.
  • Decision table testing — combinations of remember me, 2FA on or off, and SSO versus password login.
  • State transition testing — logged out, authenticating, second factor, authenticated, timed out, reset requested, reset complete.
  • Use case testing — new user, returning user, and error recovery journeys in the PRD.
  • Error guessing and exploratory testing — in addition to the written cases.

Cases are prioritized so Phase 1 login, validation, errors, and password reset run before Phase 2 UX and Phase 3 SSO and monitoring.

Step 2. When a build is ready for test:

  • Run smoke tests on sign-in, validation message, forgot password, and dashboard handoff.
  • If smoke fails, reject the build and wait for a stable build before deep testing.
  • On a stable build, execute the signed-off cases.
  • Several testers cover the environment matrix at the same time.
  • File defects in JIRA and send the day’s defects to development management.

Types used on this product: smoke and sanity, regression and retest, usability, functionality, and UI. Cycles repeat until the phase exit criteria are met.

Step 3. Practices:

  • Context-driven testing — depth follows login risk. Authentication, session, reset, and SSO get more cases than banner copy.
  • Shift-left — review the PRD and draft cases before the stable build, starting in Phase 1.
  • Exploratory testing — alongside scripted cases, especially accessibility, theme switch, and error recovery.
  • End-to-end flows — new user from login page to trial signup and introduction; returning user from login to dashboard; failed login through reset to a new session.

9. Entry and Exit Criteria

Entry and exit criteria for each phase of the testing life cycle:

Requirement analysis

Entry. The testing team has the requirements document or project details. For this work, that document is the VWO Login Dashboard PRD.

Exit. The requirements have been explored and understood. Open questions are cleared before cases are treated as final.

Test execution

Entry. Test scenarios and test cases are signed off. The application build is ready for testing.

Exit. Test case reports and defect reports are ready. For a phase exit, smoke is green, planned cases for that phase are executed, and open defects are accepted by the approvers with severity and priority set.

Test closure

Entry. Test case reports and defect reports are ready.

Exit. The test summary report is complete. The summary states results against the PRD targets that were testable in the build: login success, page load under 2 seconds, accessibility evidence, and security controls in scope. It lists open defects and any PRD item not exercised.

10. Tools

  • JIRA — defect tracking.
  • Mind map — scenario breakdown of login, recovery, and SSO.
  • Snipping and screenshot capture — defect evidence, with secrets removed.
  • Word and Excel — cases, execution records, and the summary report. This plan is the HTML copy of the test plan.

Playwright is the company automation framework for end-to-end checks. Automated smoke can cover load of the login page, email format feedback, empty submit, and navigation to the registration link. SSO, 2FA, and accessibility still need the manual cases in this plan until those flows are stable enough to automate.

11. Risks and Mitigations

Project risks from the company template, applied to this login effort:

RiskMitigation
A tester is unavailable. Backup resource planning before Phase 1 execution.
The build URL does not load. Testers switch to case design, data prep, or retest of an earlier phase until the URL is restored.
Time for testing is shorter than the three phases need. Add people to match the approved scope. Protect Phase 1 login, reset, and session cases if scope must be cut. Record any cut in the summary.

Risks the PRD already names, and how testing responds:

RiskWhat testing will do
Security of login, including brute force and session handling. Execute the security inclusions: HTTPS, rate limit, session timeout, and safe error text. The PRD also calls for audits, penetration testing, monitoring, and patches. Those activities stay with the security owners. This plan does not describe how to attack the system.
Performance under load and traffic spikes. Check the 2-second load target and run the concurrent-login cases the environment can support. The PRD assigns load testing, monitoring, and auto-scaling to the platform. Test reports the observed timings and failures.
Accessibility or compliance evidence is missing at release. WCAG 2.1 AA, GDPR, and CCPA checks in scope are mapped to cases. Gaps are defects, not informal notes.
Phase 3 SSO and social login depend on identity providers. Do not start Phase 3 execution until test identity-provider accounts exist. Password login in Phase 1 does not wait on SSO.
